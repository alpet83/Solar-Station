# Справочник по скриптам

## Обзор

Этот документ — построчный справочник по каждому исполняемому скрипту в `sbin/` и `mqtt/`: назначение, аргументы командной строки, входные и выходные файлы, зависимости от других скриптов. Про общую архитектуру и то, как эти скрипты складываются в единый пайплайн, см. [обзор](01-overview.md); про пути, устройства и константы — [конфигурацию](03-configuration.md).

### sbin/jkbms_ctrl.py

**Назначение.** Опрашивает JKBMS (Battery Management System) по протоколу JK RS485/232 через serial-порт, декодирует ответный кадр (напряжения ячеек, температуры, ток/напряжение батареи, SoC, параметры защиты BMS) и сохраняет усреднённый снимок в JSON. Также умеет отправлять на BMS команды записи/активации параметров.

**Как запускается.** Без аргументов — обычный опрос (`read_all`, команда чтения всех данных). С флагом `--cmd` в диапазоне 1–6 скрипт формирует и отправляет на BMS кадр записи/активации вместо чтения.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--cmd` | int | `0` | Код команды протокола: `1,2,3,5,6` = activate, write, read, update, read_all. `0` (по умолчанию) означает обычное чтение всех данных (`read_all`), безопасно для регулярного опроса. |
| `--id` | int | `0` | Селектор параметра BMS для операций r/w/u (`00`, `0x79`–`0xba`), передаётся как первый байт полезной нагрузки кадра. |
| `--value` | str | `''` | HEX-строка байт значения для записи параметра (используется вместе с `--cmd`/`--id` при записи). |
| `--bms_id` | int | `0` | ID конкретного BMS на шине для адресации (`0` = широковещательно, все BMS на шине). |

**Важно (безопасность).** `--cmd` в диапазоне 1–6 выполняет фактическую запись/активацию на BMS (изменение защитных порогов, включение/выключение MOS-переключателей заряда/разряда/балансировки и т.п.), а не просто чтение. Такие вызовы должны выполняться осознанно, вручную и с пониманием, какой `--id`/`--value` уходит на шину — ошибочная запись может изменить пороги защиты батареи. Пример безопасного одноразового вызова с записью — см. `sbin/jkbms_enable_chg.sh` ниже. При таймауте ответа на команду записи/активации скрипт **не** повторяет отправку автоматически (в отличие от режима чтения) — печатает предупреждение и требует ручной проверки шины.

**Что читает.** Serial-устройство `/dev/ttyBMS0` (стабильный udev-алиас, см. [конфигурацию](03-configuration.md) — константы `port`, `baud`, `signature`).

**Что пишет.** При обычном опросе (`save_res = True`, то есть без `--cmd` в диапазоне 1–6): `/tmp/jkbms_last.json` (перезапись, последний усреднённый снимок) и `/tmp/jkbms_stats.json` (дозапись, накопительный лог по строке JSON за запуск). При вызове с `--cmd` 1–6 файлы не пишутся — результат только печатается в stdout.

**От чего зависит.** Запускается из `sbin/pool_devices.sh`; результат (`/tmp/jkbms_last.json`) читают `sbin/batmon.php`, `html/index.php` и `mqtt/mqtt-client.php` (через `publish_bms()`); `/tmp/jkbms_stats.json` архивируется `sbin/backup_stats.sh`.

**Надёжность.** В рамках спринта правок весь блок `__main__` обёрнут в `try/except` с логированием и `sys.exit(1)` при непредвиденном исключении, а также добавлена защита `if __name__ == "__main__":` — за деталями см. историю git, здесь приводится не полный список изменений.

### sbin/pv1800_ctrl.py

**Назначение.** Опрашивает инвертор MUST PV1800 по Modbus RTU (через `pymodbus`, с фолбэком на `minimalmodbus`), читает регистры конфигурации и реального времени (PV-контроллер заряда, инвертор, сеть, батарея), формирует снимки состояния и накопительной статистики, а также применяет команды записи регистров из очереди `/root/inverter_cmd.lst`.

**Как запускается.** Без аргументов командной строки; при старте пытается подключиться через `pymodbus` (`using_pymodbus()`), и только если это не удалось (либо не совпал `machine_id` устройства с ожидаемым `PV1800_ID`) — пробует `minimalmodbus` (`using_mini()`). После однократного чтения полной конфигурации входит в цикл `read_loop()`, который каждые ~5 секунд вызывает `scan_realtime()` (опрос реального времени) и `parse_cmds()` (применение команд записи), пока не истечёт минута (условие `time.time() % 60 < 50`) — то есть скрипт периодически перезапускается планировщиком, а не работает бесконечно одним процессом.

**Что читает.** Serial-устройство `/dev/ttyINV0` (стабильный udev-алиас, Modbus RTU, slave `0x04`, 19200 бод — см. [конфигурацию](03-configuration.md)); очередь команд `/root/inverter_cmd.lst` (построчно `адрес=>значение`, файл удаляется после прочтения).

**Что пишет.** `/tmp/inverter_cfg.json` (конфигурация инвертора/зарядного контроллера, перезапись), `/tmp/inverter_raw.json` (сырые значения регистров, для отладки, перезапись), `/tmp/inverter_last.json` (снимок реального времени, перезапись), `/tmp/inverter_accum.json` (накопленные счётчики энергии, перезапись), `/tmp/inverter_stats.json` (накопительный лог, дозапись — только когда токи заметно изменились относительно предыдущего опроса), `/root/inverter_cmd.lst.log` (журнал обработанных команд записи, дозапись).

**От чего зависит.** Запускается из `sbin/pool_devices.sh` (в фоне, `nohup`); очередь `/root/inverter_cmd.lst` наполняется из `mqtt/mqtt-client.php` (`on_switch_set()`) и из `sbin/batmon.php` (автоматическое переключение on-grid/off-grid по уровню заряда батареи); результаты читают `sbin/batmon.php`, `html/index.php`, `mqtt/mqtt-client.php` (`publish_inverter()`) и `sbin/backup_stats.sh`.

**Надёжность.** В рамках спринта правок добавлены: обработка исключений вокруг каждой итерации `read_loop()` (чтобы сбой одного опроса не ронял процесс), клэмп под `sqrt` в `calc_p()` (`math.sqrt(max(0, s*s - q*q))`, чтобы отрицательное подкоренное значение из-за шума данных не вызывало `ValueError`), правки веток `minimalmodbus`/`pymodbus` (несогласованность в выборе клиента), и защита `if __name__ == "__main__":` — за полным списком изменений обращайтесь к истории git, здесь не приводится весь патч.

### mqtt/mqtt-client.php

**Назначение.** Долгоживущий процесс-мост между локальными JSON-снимками (`/tmp/jkbms_last.json`, `/tmp/inverter_last.json`, `/tmp/inverter_accum.json`, `/tmp/inverter_cfg.json`) и MQTT-брокером Home Assistant: публикует Home Assistant discovery-конфиги и телеметрию, а также принимает обратные команды переключателей.

**Как запускается.** `php mqtt-client.php [любой-аргумент]` — если передан хотя бы один аргумент (`$argc > 1`), учётные данные MQTT берутся из `/etc/MQTT_creds` (формат `user password`), иначе используется заглушка `'user password'`. Аргументов с явной семантикой (флагов) скрипт не разбирает — единственное, что проверяется, это сам факт наличия аргумента. После подключения публикует discovery-конфиги (через `MqttConfigFactory`) и входит в цикл до конца текущего часа (`while ($minute < 59)`), внутри которого каждую итерацию вызывает `publish_bms()`, `publish_inverter()` и `$mqtt->loopOnce()`.

**Два направления работы:**
- **Публикация телеметрии** — `publish_bms()` и `publish_inverter()` читают соответствующие `/tmp/*.json`, проверяют свежесть данных (`OUTDATED_TRESH` минут) и публикуют показания и состояния переключателей в MQTT-топики.
- **Приём команд** — `on_switch_set()` подписан на command-топики Home Assistant switch-сущностей; при получении сообщения дописывает строку `адрес=>значение` в `/root/inverter_cmd.lst`, откуда её позже заберёт `sbin/pv1800_ctrl.py`.

Подробности по структуре MQTT-топиков и настройке интеграции с Home Assistant — в отдельном документе [MQTT/Home Assistant интеграция](05-mqtt-ha-integration.md), здесь они не дублируются.

**Что читает.** `/tmp/jkbms_last.json`, `/tmp/inverter_last.json`, `/tmp/inverter_accum.json`, `/tmp/inverter_cfg.json`; JSON-описания discovery-шаблонов `mqtt/bms_sensor.json`, `mqtt/bms_switch.json`, `mqtt/inverter_sensor.json`, `mqtt/inverter_sw.json`; при запуске с аргументом — `/etc/MQTT_creds`.

**Что пишет.** `/root/inverter_cmd.lst` (дозапись, команда для `pv1800_ctrl.py`); в остальном — публикует в MQTT, локальных файлов состояния не создаёт.

**От чего зависит.** Запускается (условно — только если ещё не запущен) из `sbin/pool_devices.sh`; напрямую зависит от актуальности снимков, которые пишут `sbin/jkbms_ctrl.py` и `sbin/pv1800_ctrl.py`.

### sbin/batmon.php

**Назначение.** «Сторож» батареи: проверяет свежесть и разумность показаний BMS/инвертора, шлёт алерты во внешний телеграм-бот при отклонениях (низкое/высокое напряжение ячейки, аномальный ток), и автоматически переключает инвертор в режим on-grid/off-grid — не по разовому порогу, а по счётчику-гистерезису (5 подряд «согласных» запусков в одну сторону), учитывающему суммарный ток заряда сразу от двух источников (встроенный контроллер PV1800 + внешний Epever MPPT). Также ежедневно в промежутке 15:00–21:59 (в начале часа) шлёт сводный отчёт о состоянии. Подробности порогов и формулы — в [конфигурации](03-configuration.md#пороги-batmonphp).

**Как запускается.** `php batmon.php [offgrid_start]` — предполагается регулярный запуск планировщиком (cron, каждые 5 минут). Необязательный первый аргумент переопределяет порог напряжения `$offgrid_start` (по умолчанию 3.32 В), с которого начинается отсчёт на отключение сети.

**Что читает.** `/tmp/jkbms_last.json` (обязателен, свежесть проверяется по `ts`, скрипт завершается фатальной ошибкой при отсутствии/невалидности), `/tmp/inverter_cfg.json` (поле `config->ongrid_switch`), `/tmp/inverter_last.json` (текущая мощность нагрузки/инвертора и зарядный ток PV-контроллера), `/tmp/inverter_accum.json` (накопленная энергия для отчётов), `/tmp/epever_dump.json` (ток заряда от внешнего MPPT-контроллера Epever — **пишется скриптом вне этого репозитория**, `/usr/local/sbin/epever_dump.sh`; если файла нет или в нём нет `battery_current`, эта составляющая тока считается нулём и в лог пишется предупреждение), `/tmp/on_grid.cntr` (свой же счётчик гистерезиса с прошлого запуска), `/etc/hostname`, `/etc/telebot` (URL сервиса уведомлений).

**Что пишет.** `/tmp/on_grid.cntr` (перезапись — новое значение счётчика гистерезиса), `/root/inverter_cmd.lst` (команда `20105=>1` или `20105=>0` — но только в момент, когда счётчик гистерезиса впервые достигает крайнего значения, не на каждом запуске), `/dev/kmsg` (текстовое сообщение о событии переключения), плюс HTTP-запросы к сервису уведомлений (`send_event()`; при ответе с `#ERROR` пишет в STDERR вместо обычного лога).

> **Несогласованность режима записи.** В отличие от `on_switch_set()` в `mqtt/mqtt-client.php` (которая после фикса из спринта правок дописывает команду через `FILE_APPEND`), `batmon.php` пишет в `/root/inverter_cmd.lst` через обычный `file_put_contents()` без дозаписи, то есть **перезаписывает** файл целиком. Если `batmon.php` и MQTT-команда от Home Assistant совпадут по времени в пределах одного цикла опроса `pv1800_ctrl.py`, одна из двух команд может быть потеряна. Стоит унифицировать оба места на дозапись при последующей доработке (см. [Безопасность и планы по авторизации](08-security-roadmap.md)).

**От чего зависит.** Требует свежих `/tmp/jkbms_last.json`, `/tmp/inverter_cfg.json` и `/tmp/inverter_last.json`, которые пишут `sbin/jkbms_ctrl.py` и `sbin/pv1800_ctrl.py`; опционально — `/tmp/epever_dump.json` от стороннего `epever_dump.sh`; команды переключения, которые он ставит в очередь `/root/inverter_cmd.lst`, забирает `sbin/pv1800_ctrl.py`.

### sbin/pool_devices.sh

**Назначение.** Главный скрипт запуска всего пайплайна опроса устройств: синхронизирует время, активирует Python virtualenv, запускает опрос инвертора и BMS, копирует логи на веб-сервер и (при необходимости) поднимает MQTT-клиент.

**Как запускается.** `sh pool_devices.sh` (или `bash`), без аргументов; предполагается запуск планировщиком (cron) с регулярным интервалом. Внутри: `cd /home/alpet/solar`, `ntpdate pool.ntp.org` (синхронизация времени), `source ./venv/bin/activate` (Python virtualenv), затем `pv1800_ctrl.py` в фоне (`nohup ... &`) и `jkbms_ctrl.py` синхронно (дожидается завершения). После этого копирует `~/root/inverter*.log` в `/var/www/html`, ждёт 5 секунд и проверяет, не запущен ли уже `mqtt-client.php` (через `ps x | grep php`) — если не запущен, стартует его.

**Что читает.** Список процессов через `ps x` (косвенно, для проверки `mqtt-client.php`); файлы `~/root/inverter*.log` (для копирования).

**Что пишет.** `/tmp/pv1800_ctrl.log`, `/tmp/pv1800_ctrl.err`, `/tmp/jkbms_ctrl.log`, `/tmp/jkbms_ctrl.err` (stdout/stderr дочерних процессов), `/var/www/html/inverter*.log` (копия логов для веб-доступа), `/tmp/php.lst` (список php-процессов), `/tmp/mqtt_client.nfo` (пометка, что MQTT-клиент уже был запущен) либо `/tmp/mqtt-client.log` (лог запуска MQTT-клиента).

**От чего зависит.** Запускает и `sbin/jkbms_ctrl.py`, и `sbin/pv1800_ctrl.py`, и (условно, если ещё не запущен) `mqtt/mqtt-client.php` — то есть является точкой входа, объединяющей весь набор скриптов; подразумевает наличие virtualenv `./venv` относительно `/home/alpet/solar`.

### sbin/backup_stats.sh

**Назначение.** Архивирует накопленные за день JSON-логи BMS и инвертора в сжатом виде для долговременного хранения.

**Как запускается.** `sh backup_stats.sh`, без аргументов; предполагается ежедневный запуск планировщиком (cron), обычно после полуночи (используется текущая дата `date +'%Y-%m-%d'` для имени файла). Внутри скрипта — пауза `sleep 15` перед архивацией (даёт время другим процессам завершить запись).

**Что читает.** `/tmp/jkbms_stats.json`, `/tmp/inverter_last.json`.

**Что пишет.** `/backup/jkbms/stats_ГГГГ-ММ-ДД.json.gz`, `/backup/inverter/stats_ГГГГ-ММ-ДД.json.gz` (сжатие `gzip --best`). Исходные `/tmp`-файлы не удаляются (строка `rm /tmp/jkmbs_stats.json` закомментирована).

**От чего зависит.** Зависит от того, что `sbin/jkbms_ctrl.py` и `sbin/pv1800_ctrl.py` регулярно обновляют `/tmp/jkbms_stats.json` и `/tmp/inverter_last.json`; каталоги `/backup/jkbms` и `/backup/inverter` должны существовать заранее.

### sbin/jkbms_enable_chg.sh

**Назначение.** Одноразовая обёртка над `jkbms_ctrl.py` для включения заряда через MOS-переключатель заряда (`chg_MOS_switch`, параметр `0xab` = 171 в десятичном виде) на BMS.

**Как запускается.** `sh jkbms_enable_chg.sh`, без аргументов. Внутри вызывает `jkbms_ctrl.py --cmd 2 --id 171 --value '01'` — команда `2` (write), параметр `171` (`0xab`, `chg_MOS_switch`), значение `01` (включить).

**Важно (безопасность).** Это тот самый случай прямой записи на BMS, описанный выше в разделе `jkbms_ctrl.py` — команда `--cmd 2` изменяет состояние MOS-переключателя заряда батареи. Запускать вручную и осознанно, не встраивать в регулярный автоматический пайплайн без явной необходимости.

**Что читает/пишет.** Не читает и не пишет собственные файлы состояния; перенаправляет вывод `jkbms_ctrl.py` в `/tmp/jkbms_enable_chg.log`.

**От чего зависит.** Требует `jkbms_ctrl.py` в `PATH` (обычно `/usr/sbin/jkbms_ctrl.py`) и доступа к serial-порту BMS.

### html/index.php

**Назначение.** Простая веб-страница статуса станции: выводит HTML-таблицы с показаниями BMS (напряжения ячеек, температуры, статусы переключателей) и инвертора/PV-контроллера (напряжения, токи, мощности, режимы, ошибки/предупреждения) для просмотра в браузере.

**Что читает.** `/tmp/jkbms_last.json`, `/tmp/inverter_cfg.json`, `/tmp/inverter_last.json`, а также текстовые справочники кодов ошибок/предупреждений инвертора `inv_errors_1.txt`, `inv_errors_2.txt`, `inv_warns_1.txt` (относительно рабочей директории `html/`). Ничего не пишет — read-only страница.

**От чего зависит.** Полностью зависит от свежести снимков, которые пишут `sbin/jkbms_ctrl.py` и `sbin/pv1800_ctrl.py`; при устаревших данных (>10 минут) или отсутствии файлов страница завершает вывод фатальной ошибкой (`die()`).
