# grid-supervisor

Прошивка LilyGo T-CAN485: независимый от Raspberry Pi контроль переключения инвертора
MUST PV1800 между сетью и батареей (пишется только регистр 20105).
Принцип: подключение к сети разрешено всегда, отключение — только при полной уверенности.

- `lib/gs_core` — переносимое ядро без Arduino-зависимостей;
- `test/native` — тесты ядра и реплей инцидента (`make test`);
- `lib/gs_can` — разбор CAN-кадров батареи (чистая логика, тесты `test/native/test_gs_can.cpp`);
- `lib/gs_notify` + `src/notify.cpp` — вебхук-уведомления (раздел «Вебхук-уведомления», тесты `test/native/test_gs_notify.cpp`);
- `docs/calibration.md` — калибровка порогов.

## OTA поверх BatteryEmulator
Схема разделов (`min_spiffs`, слот приложения ~1.9 МБ) и загрузчик по OTA не меняются.
Первый образ обязан содержать рабочий OTA; восстановление — USB-C. Откат при неудачной
загрузке не проверен.

## Сборка
`make test` — нативные тесты. `pio run -e lilygo_330` — ESP32 (на ПК пользователя).

## Режим сниффера и сожительство с даталоггером

Плата пассивно разбирает кадры Modbus на шине (`lib/gs_bus`) и выучивает ритм второго мастера
(SmartESS-логгер, пачка запросов раз в ~5 мин): `GET /api/sniff` — итог по ритму, последние пачки
и кадры (`locked`, `period_ms`, `next_start_in_ms`, `bursts[]`, `frames[]`, времена в UTC).
В обычном режиме плата молчит во время пачки и за ~8 с до предсказанного начала, а между пачками
опрашивает чаще (3 с вместо 5 с). Решения принимаются только по данным, прочитанным в текущем цикле.
Команда «подключить сеть» ритмом не ограничивается (только реальной занятостью шины).

`POST /api/logger period_s=30..900` — ожидаемый период пачек логгера (по умолчанию 90 с: по захвату трафика стика облако SmartESS опрашивает инвертор полным циклом из ~10 запросов (~5,5 с) каждые ~90 с, а записи в приложении сохраняются каждые ~3 мин; хранится в NVS, сбрасывает захват). `POST /api/mode m=sniff|normal` (с заголовком `X-GS`) — режим только приёма: плата ничего не
передаёт, ядро не работает, **управления сетью нет** (управляет Pi как раньше), кэш `/api/regs`
не обновляется, `/api/cmd` отвечает 409. Войти нельзя, пока `20105=0` (сеть заведомо отключена, в sniff защит нет); если данных нет вовсе, можно; режим хранится в NVS,
но отменяется safe-mode (после аварийных перезагрузок). Используйте для калибровки ритма на
несколько часов, затем верните `normal`.

## Первая прошивка поверх BatteryEmulator: как не потерять доступ

После OTA в NVS платы пусто (настройки BatteryEmulator не импортируются). Плата сразу поднимает
точку доступа `gs-setup-XXXX` с паролем **`gs-<ревизия сборки>`** (ревизия — короткий хэш git на
момент сборки, суффикс `x` = были незакоммиченные правки; видна в Serial `gs rev ...` и на странице
`/setup`; собирайте после коммита). Подключитесь к AP, откройте `http://192.168.4.1/setup`:
до 4 сетей Wi-Fi по приоритету (1 — основная, остальные — резервные; при потере связи плата
перебирает их по кругу, а на резервной раз в 5 мин ищет более приоритетную), имя хоста, пароль
администратора (обязателен), свой пароль AP, токен для Pi. Сохранение перезагружает плату;
перепрошивка для смены сетей не нужна. Пароль по умолчанию фактически известен (хэш публичного
коммита): AP живёт только пока Wi-Fi ни разу не подключился, но задайте свой пароль AP в `/setup`.
Если Wi-Fi недоступен вовсе, остаётся AP; при полном провале — USB-C и прошивка BatteryEmulator обратно.

## Консоль по Serial (USB-C, 115200)

Раз в 30 с и сразу при смене состояния печатается строка статуса сети, например
`net: STA up ssid='MyWiFi' ip=192.168.1.50 rssi=-58 dBm net#1/2 | AP off`
(или `STA down, trying #2 '...'`, `AP on ssid=gs-setup-XXXX ip=192.168.4.1`).
Строки вводятся прямо в терминале (`pio device monitor`, `miniterm`); пароль доступа не нужен — доверенным
считается физический доступ к USB. Команды: `help`, `status`, `nets`, `net <1..4> <ssid> [pass]`
(без пароля = открытая сеть; значения с пробелами в кавычках), `net <1..4> del`, `host`, `ap <пароль>`,
`admin <пароль>`, `mode [sniff|normal]`, `can [off|100|125|250|500]`, `logger <30..900>`, `log [on|off]` (периодическая строка
телеметрии, чтобы не мешала вводу), `webhook …` (см. «Вебхук-уведомления»), `reboot`. Сети применяются сразу, без перезагрузки; результат виден по строке статуса (`STA up … ip=…` или `STA down … err=… (network not found / wrong password?)`). `scan` показывает видимые сети (проверить написание SSID и что сеть 2.4 ГГц), `export` печатает все настройки в виде команд: сохраните вывод в файл и восстановите после сброса `tools/gs_send.sh <порт> файл` (по строке за раз; строки с `#` — комментарии), `token` задаёт токен для `/api/ext`. `mode sniff` по
Serial нужен, чтобы перевести плату в режим приёма до первого подключения к шине.

## Светодиод (WS2812, GPIO4)

Цикл 7 с: белый 1 с · сеть 1 с · синий 1 с · инвертор 3 с.
Сеть: зелёный — Wi-Fi есть и API опрашивается (запрос за последнюю минуту), жёлтый — Wi-Fi есть, запросов нет, оранжевый — проблемы MQTT (на плате MQTT пока нет), красный — нет Wi-Fi, пурпурный — режим настройки (AP).
Инвертор: длинный красный — нет связи (блок реального времени не читался 45 с); короткие мигания красный/оранжевый — связь есть, но есть проблемы (низкое напряжение, сомнительные данные, safe-mode, повтор команды, расхождение реле и т.п.); зелёный — всё в порядке, работаем от сети; бирюзовый — всё в порядке, автономный режим; фиолетовый — режим sniff (плата не управляет). Яркость `GS_LED_BRIGHT` (0..255, по умолчанию 40), пин `GS_PIN_LED`.

## CAN-сниффер батареи (Seplos BMS 3.0)

Плата пассивно слушает CAN батареи и показывает аварии BMS, разрешения заряда/разряда (МОСФЕТЫ), напряжение,
ток, SOC и лимиты пакета. **Ничего не передаётся**: драйвер TWAI в режиме `TWAI_MODE_LISTEN_ONLY` (ACK не выставляется),
очередь передачи отключена. Работает в отдельной задаче FreeRTOS (`src/can_rx.cpp`), RS485 и ядро не затрагивает.
По умолчанию включён, 500 кбит/с (так в мануале Seplos; протокол по умолчанию — Pylontech-совместимый, кадры BMS ~1 с).

**Реальная батарея (наблюдение на проводе): 100 кбит/с, расширенные 29-битные ID, dlc 8, little-endian, каждый кадр ~1 Гц** — это НЕ Pylon.
Нужно `can 100` и обязательно `ack=1` (`POST /api/can ack=1`): без ACK BMS бесконечно повторяет первый кадр и остальные не приходят
(данные при этом по-прежнему не передаются, только ACK-биты). Декодер `SeplosBattery` (`lib/gs_can`) разбирает 4 кадра; Pylon-декодер работает
параллельно по 11-битным ID 0x351…, оба кормятся одним потоком, в `battery` попадает тот, чей кадр пришёл позже (`protocol`: `"pylon"` / `"seplos_100k"` / `null`).
**Все раскладки Seplos 100k — гипотезы по значениям, документации нет** (`"confidence":"guess"` в `/api/can`):

| ID | байты (u16 LE) | поля | уверенность |
|---|---|---|---|
| `0x00030100` | `40 02 08 07 D0 01 08 07` | 576 → `charge_v_max` 57,6 В; 1800 → `charge_a_max` 180,0 А; 464 → `discharge_v_min` 46,4 В; 1800 → `discharge_a_max` 180,0 А (шаг 0,1) | высокая (значения 16S LFP / 280 А·ч правдоподобны) |
| `0x00030200` | 8 байт, сейчас нули | `prot_raw` (сырые байты), `alarm` = есть ненулевой байт; расшифровки битов нет (`protect`/`alarms` = `null`) | раскладка неизвестна; нули = «нет аварий» — предположение |
| `0x00030400` | `1B 02 6F 00 1D 00 …` | 539 → `v` 53,9 В (сходится с инвертором 53,6–53,7 В); 111 → `i_abs` 11,1 А (**знак не известен**, поэтому `i` = `null`); 29 → `temp_c` 29 °C | `v` высокая; `i_abs` средняя; `temp_c` предположительно |
| `0x00030500` | `46 00 60 00 C1 02 …` | 70 → `soc` %; 96 → `soh` % (вероятно); 705 → `soc10` = SOC в 0,1 % (70,5 %, вероятно; не остаток А·ч) | вероятно |

`charge_en` / `discharge_en` и `protect`/`alarms`/`mfr` для этого протокола всегда `null` (в кадрах их нет). Остальные ID (в т.ч. неизвестные расширенные) попадают только в таблицу `ids`.

**Режим BMS «0. Pylon CAN» (экранный пункт 0) выдаёт другой поток: 500 кбит/с, СТАНДАРТНЫЕ 11-битные ID 0x311…0x322, dlc 8, каждый кадр раз в секунду, поля u16 BIG-endian**
(старший байт первым; в старом 100-кбит/с-потоке — little-endian). Прежние 100-кбит/с-кадры с расширенными ID приходили в другом состоянии BMS. Нужно `speed=500` и обязательно `ack=1`
(`POST /api/can speed=500 ack=1`), иначе BMS повторяет первый кадр. Декодер `Seplos500Battery` (`lib/gs_can`) разбирает кадры по стандартному ID 0x311…0x322 автоматически;
Pylon-ID (0x351…) в этот диапазон не входят, стандартный 0x351 по-прежнему идёт в Pylon-декодер, расширенные кадры 500k-декодер игнорирует. Три декодера кормятся одним потоком,
в `battery` попадает тот, чей кадр пришёл последним (`protocol`: `"pylon"` / `"seplos_100k"` / `"seplos_500k"`). Документации нет, раскладка — по значениям; `"confidence":"partial"`
(ячейки/мин/макс/V/SOC/SOH уверенно, остальное — средне или guess). Свежесть (10 с) и `age_ms`/`stale` ведутся по группам кадров: `cells` (самый старый из полученных 0x315–0x318), `pack`, `minmax`, `limits`, `cap`, `temps`, `flags`.

| ID | байты (u16 BE), реальный пример | поля | уверенность |
|---|---|---|---|
| `0x311` | `02 40 07 08 07 08 00 6A` | 0x0240 → `charge_v_max` 57,6 В (16S × 3,6 В); 0x0708 → `charge_a_max` 180,0 А; 0x0708 → `discharge_a_max` 180,0 А (шаг 0,1; порядок «V, I, I» — догадка); байты 6–7 = 0x006A — неизвестно (`unk.f311`) | 57,6 В — средне; токи — guess; байты 6–7 — неизвестно |
| `0x312` | `00 00 00 00 01 00 00 10` | флаги состояния/аварий — расшифровки нет, только сырые байты `flags_raw`; `alarm` / `charge_en` / `discharge_en` остаются `null` | неизвестно |
| `0x313` | `15 01 00 3F 01 29 48 60` | б0–1: `v` = 0x1501 × 0,01 = 53,77 В; б2–3: `i_raw` = int16 × 0,1 А (0x003F = 6,3 А; **знак/направление не подтверждены**, поэтому `i` = `null`, модуль в `i_abs`); б4–5: `temp_c` int16 × 0,1 °C (29,7); б6: `soc` % (72); б7: `soh` % (96) | `v`, `soc`, `soh` — уверенно; `i_raw`, `temp_c` — средне |
| `0x314` | `52 04 71 48 00 03 01 72` | б0–1: `cap_remaining_ah` = 20996 × 0,01 = 209,96 А·ч; б2–3: `cap_full_ah` = 29000 × 0,01 = 290,00 А·ч; б4–5: счётчик (3 → 2, неизвестен; `unk.f314_cnt`); б6–7: `cycles` = 370 (209,96 / 290 = 72,4 % согласуется с SOC 72 %) | всё guess |
| `0x315`–`0x318` | `0D 1F 0D 20 0D 20 0D 20` … | напряжения 16 ячеек, u16 BE, мВ, по 4 в кадре, по порядку: 0x315 — ячейки 1–4, 0x316 — 5–8, 0x317 — 9–12, 0x318 — 13–16; `cells_mv[16]` (сумма 53,765 В ≈ `v`) | уверенно |
| `0x319` | `C0 0D 22 0D 1F 01 01 00` | б1–2: `cell_max_mv` = 3362; б3–4: `cell_min_mv` = 3359; `cell_delta_mv` = max − min; б0 (0xC0) и б5–6 (индексы 01 01, смысл не ясен) — неизвестно (`unk.f319`) | мин/макс — уверенно (совпадают с диапазоном ячеек); остальное — неизвестно |
| `0x320` | `47 54 0A 0A 00 00 00 00` | неизвестно (возможно ASCII «GT» + …), сырьё `unk.f320` | неизвестно |
| `0x322` | `01 29 01 1D 01 01 48 48` | б0–1: `temp_max_c` 29,7 °C; б2–3: `temp_min_c` 28,5 °C (вероятно макс./мин. температура ячеек, 0,1 °C); б4–5 (`01 01` — индексы) — неизвестно (`unk.f322`, наблюдается триггерами); б6–7 (`48 48` = 72 72) повторяют SOC (0x48/0x49/0x3f/0x3e менялись по мере разряда) — шум, триггерами НЕ наблюдаются | guess |

Правила: если `cell_min_mv`/`cell_max_mv` из 0x319 расходятся с массивом ячеек, берутся значения 0x319 (`cell_delta_mv` = max − min по ним); без свежего 0x319, но при свежих всех 16 ячейках диапазон считается по массиву.
В `cells_mv` ячейка без свежего кадра = `null`, весь массив `null`, если нет ни одной. В `/api/state` → `battery` для этого протокола `i` = `null`, ток в `i_abs`.

- Подключение: разъём CAN на BMS (RJ45/8P8C): 4 = CAN-H, 5 = CAN-L, 3 и 6 = GND (по документации Seplos). На плате
  T-CAN485 клеммы CAN H / CAN L / GND. Сниффер подключается параллельно инвертору (отводом от линии) или в разрыв
  вместо него; терминатор 120 Ом нужен на концах линии: если на шине уже есть инвертор и BMS с терминаторами, не добавляйте;
  если плата одна с BMS на коротком кабеле — включите 120 Ом на плате (перемычка/резистор), иначе возможны ошибки кадров.
- Пины (переопределяются `-D`): TX=IO27, RX=IO26 (TX физически не используется), CAN_SE=IO23 (`GS_CAN_SE_ON`, по умолчанию LOW = трансивер работает).
- Консоль: `can` — состояние, `can off|100|125|250|500` — выключить / скорость (хранится в NVS; при смене счётчики и таблица сбрасываются);
  состояние видно и в `status`, настройка — в `export`. Признак неверной скорости: `bus_errors` растёт, а `rx_msgs` нет.
- `POST /api/can speed=0|100|125|250|500 [ack=0|1]` (пароль + `X-GS`): скорость и подтверждение кадров. `ack=1` — узел работает в режиме normal без очереди передачи: в шину уходят только ACK-биты (нужно, если BMS — единственный узел и без подтверждения повторяет кадры бесконечно; данные не передаются). По умолчанию `ack=0` (чистый listen-only).
- `hb=1` (в том же POST): раз в секунду слать кадр `0x305` (стандартный, 8 нулей) — «жив» инвертора из Seplos CAN V1.0; в режиме Pylon BMS молчит, пока его не услышит. Это единственная передача данных платой в CAN; по умолчанию выключено. Включает ACK. Подключайте только к батарее, не к шине с инвертором.
- `GET /api/can` (чтение открыто, как `/api/state`): `driver` (`state`, `rx_msgs`, `rx_missed`, `bus_errors`, `bus_off_count`),
  таблица `ids` (до 24 ID: hex, `count`, `period_ms`, `age_ms`, последние данные; неизвестные ID тоже), блок `battery`:
  `v` `i` (+ заряд, − разряд) `temp_c` `soc` `soh`, лимиты `charge_v_max` `charge_a_max` `discharge_a_max` `discharge_v_min`,
  `charge_en` `discharge_en` `force_charge` (кадр 0x35C — разрешения МОСФЕТОВ BMS), `alarm`, `protect[]` (отключения, байты 0–1 кадра 0x359),
  `alarms[]` (предупреждения, байты 2–3), `prot_raw`, `modules`, `mfr`. Для каждого кадра `age_ms` и `stale`: кадр старше 10 с — значения `null`
  (в том числе `alarms`/`protect`: `[]` = аварий нет, `null` = неизвестно). Неопознанный бит аварии выводится как `P1.b5` / `A2.b1`.
  Дополнительно: `protocol`, `confidence` (`"guess"` для Seplos 100k, `"partial"` для Seplos 500k, `null` для Pylon), `i_abs` (только Seplos), `soc10` (только Seplos 100k).
  Для `seplos_500k` добавляются: `cells_mv` (16 чисел, мВ, или `null`), `cell_min_mv`, `cell_max_mv`, `cell_delta_mv`, `i_raw` (со знаком, знак не подтверждён), `temp_max_c`, `temp_min_c`, `cap_remaining_ah`, `cap_full_ah`, `cycles`, `flags_raw` (сырые байты 0x312), блок `unk` (сырьё неизвестных полей).
- `GET /api/state` содержит `"battery":{"v","i","soc","charge_en","discharge_en","alarm","age_s","i_abs","protocol","cell_min_mv","cell_max_mv","cell_delta_mv"}` (`null`, если свежих данных нет; для Seplos `i` всегда `null`, ток в `i_abs`; `cell_*` — только `seplos_500k`, иначе `null`).
- Режим приёма (`mode sniff`) к CAN отношения не имеет: CAN всегда только слушает.
- Счётчики: `bus_errors`/`rx_missed` берутся из драйвера и сбрасываются при смене скорости. bus-off (в listen-only маловероятен)
  → автоматический `twai_initiate_recovery()` + `twai_start()`, учитывается в `bus_off_count`.

Не проверено на железе: уровень CAN_SE, пины, раскладка кадров 0x359/0x35C (в PDF Seplos её нет — взята по описанию протокола Pylontech),
знак тока, вся раскладка Seplos 100k и все поля Seplos 500k, кроме помеченных «уверенно» (таблицы выше — гипотезы; знак тока 0x313, смысл 0x312/0x320/0x322/0x314-счётчика и индексов в 0x319 неизвестен), прочие расширенные ID Seplos (не декодируются; попадают в таблицу `ids`),
сборка `driver/twai.h` под используемый IDF.

## Защита по самой слабой ячейке, триггеры BMS, `/api/bms_events`

Только для `seplos_500k` (ячейки даёт кадр 0x319 / массив 0x315–0x318, свежесть 10 с). Для остальных протоколов и без свежих кадров `cell_min_v = NaN`, и ядро работает как раньше.

**Ядро** (`gs::Config`, ключи есть в `/api/config`, NVS и `POST /api/config`; в конце списка полей, прежние индексы NVS не сдвинуты):

| ключ | по умолчанию | смысл |
|---|---|---|
| `cell_hard_floor_v` | 2.90 | ячейка ≤ порога дольше `hard_dwell_ms` → подключить сеть (как `hard_floor_v`: перебивает ручную паузу) |
| `cell_soft_on_v` | 3.05 | ячейка ≤ порога дольше `soft_on_dwell_ms` → подключить сеть (как `soft_on_v`: молчит в ручной паузе) |
| `cell_off_min_v` | 3.20 | при свежих данных и ячейке НИЖЕ порога от сети не отключаемся (выдержка «заряжено» тогда не копится и начнётся заново) |
| `cell_guard` | 1 | 0 — ячейки игнорируются; 1 — учитываются, когда данные свежие; 2 — как 1, и если ячейки в этом запуске были видны, а свежих данных сейчас нет, от сети не отключаемся |

Валидация: каждый порог 2.5…3.65 В, строго `hard < soft < off_min`, `cell_guard ≤ 2`. Условие ячейки добавляется к условию по пакету через ИЛИ (подключение) и через И (отключение).
Причины команд прежние (`HARD_FLOOR` / `SOFT_LOW`), различаются флагами: `CELL_HARD`, `CELL_LOW` (таймер по ячейке идёт; `HARD_LOW`/`SOFT_LOW` остаются только за пакетом) и `CELL_BLOCK`
(отключение заблокировано ячейками, в т.ч. ручное). Таймеры ячеек независимы от опроса инвертора и при пропаже данных не сбрасываются (сторона сети). Ручное отключение тоже требует `cell_off_min_v`. `/api/state` → `"guard":{"cell_min_v":3.241|null,"cells_seen":bool,"cell_block":bool}`.
`cells_seen` сбрасывается перезагрузкой и сменой скорости CAN.

**Триггеры** (`lib/gs_trig`). Генерация: задача CAN после каждого кадра и раз в ~0.5 с (под mutex'ом) строит `BmsSnapshot` и вызывает `BmsWatch::update`, который кладёт события в `TriggerQueue` (32, при переполнении вытесняются старые, счётчик `dropped`)
и в журнал `BmsEventLog` (16). События — только по переходам: `CELL_LOW`/`CELL_LOW_OK` (порог `cell_soft_on_v`, выход +30 мВ), `CELL_HARD`/`CELL_HARD_OK` (`cell_hard_floor_v`), `CELL_DELTA` (> 100 мВ) / `CELL_DELTA_OK` (< 70 мВ),
`BMS_STALE` (нет кадров > 10 с, один раз; не раньше первого кадра) / `BMS_BACK`, `BMS_FLAGS` — изменение «знакового» сырого поля (первое значение — baseline без события; одно поле не чаще раза в 5 с, изменения внутри окна сливаются).
Наблюдаются: 0x312 и 0x320 (8 байт), 0x319 (байт 0 и индексы), 0x322 байты 4–5 (байты 6–7 повторяют SOC — шум), 0x311 байты 6–7 (500k); `prot_raw` 0x00030200 (100k); 0x359 protect/alarm и 0x35C (Pylon). Ток, напряжения, температуры, ёмкость, счётчик 0x314 не наблюдаются.
Текст: `f312 0000000001000010->0000000001000012` (old->new в hex; 8-байтовые поля — без пробелов, чтобы влезть в 47 символов; короткие — `f319 c0 03 07 -> c0 04 07`).
Обработка: цикл управления раз в итерацию выгребает очередь, печатает `TRIG #id TAG ...` в Serial и передаёт триггер в `notify::push` (вебхук, см. «Вебхук-уведомления»).

**`GET /api/bms_events`** (чтение открыто, как `/api/state`): `{"total":N,"now_ms":..,"events":[{"id","t_ms","age_s","ts"(UTC|null),"tag","sev"(info|warn|alert),"value","text"}]}`, от новых к старым, последние 16 с момента загрузки.
Проверка занижения напряжения полного заряда: понизьте его в BMS и смотрите `BMS_FLAGS` с полями `f312`/`f320`/`f319` (какой байт/бит изменился — в `text`, номер поля и маска изменившихся байт — в `aux` триггера в Serial).

## Вебхук-уведомления

Плата сама шлёт HTTP-запрос на любой http/https-сервис (Telegram-бот, ntfy, Home Assistant, свой `reg_event.php`), не блокируя цикл управления:
`lib/gs_notify` — чистая логика (шаблоны, очередь, преобразование событий; тесты `make test`), `src/notify.cpp` — отдельная задача FreeRTOS `gs_notify`
(приоритет 1, стек 12 КБ, ядро 0), `HTTPClient`. Цикл управления только вызывает `notify::push()` (mutex с таймаутом 0; занят — событие считается потерянным и
попадает в `dropped`). Отправка — **только когда есть Wi-Fi**; пока его нет, события копятся в кольце на 16 (старые вытесняются). Выключенный вебхук событий не копит.
Имена плейсхолдеров, методы и ключи совпадают с встроенным вебхуком прокси `sbin/eybond_tap.py` (`builtin:webhook`), поэтому один URL-шаблон годится и для прокси, и для платы.

### Настройка

Консоль (значение — остаток строки как есть; в кавычках можно `\"` и `\\`; пустое значение — `""`):

| команда | смысл |
|---|---|
| `webhook` | статус: вкл/выкл, метод, **только схема+хост** URL (путь и query с токеном не показываются), длины, счётчики, последний результат |
| `webhook url <url>` | URL-шаблон, `http://` или `https://`, до 255 символов, без пробелов (пробел — `%20`) |
| `webhook method get\|post` | метод (по умолчанию GET) |
| `webhook body <шаблон>` | тело для POST (до 400 символов) |
| `webhook ctype <тип>` | Content-Type для POST (по умолчанию `application/x-www-form-urlencoded`) |
| `webhook err <подстрока>` | ответ с этой подстрокой считается сбоем (как `alert_webhook_error_text`); `""` — не проверять |
| `webhook timeout <1..60>` | таймаут запроса, с (10) |
| `webhook min info\|warn\|alert` | минимальная серьёзность (по умолчанию `warn`) |
| `webhook insecure on\|off` | https без проверки сертификата (по умолчанию `on`) |
| `webhook on` / `off` | включить / выключить (включить без URL нельзя) |
| `webhook test` | поставить в очередь событие `TEST` (обходит фильтр серьёзности и подавление повторов) |

`export` печатает строки восстановления (`webhook url "…"`, `method`, `body`, `ctype`, `err`, `timeout`, `min`, `insecure`, `on`) — как и пароли, вывод секретный (в URL/теле токены).
Хранится в NVS (пространство `gs`, ключи `wh_url wh_method wh_body wh_ctype wh_err wh_tmo wh_min wh_insecure wh_en`). `${host_name}` — имя хоста из настройки `host`.

Страница `/setup` (только под паролем администратора; пока пароль не задан, секция вебхука скрыта — в URL может быть токен бота): поля URL, метод, Content-Type, тело,
текст сбоя, таймаут, минимальная серьёзность, `insecure`, `enabled`; пустое текстовое поле = очистить. Плата после сохранения перезагружается, как и для остальных полей `/setup`.

HTTP:
- `GET /api/webhook` (чтение открыто, **без секретов**): `{"enabled","host"(из URL, без пути/query/userinfo),"method","min_sev","timeout_s","insecure","sent","failed","dropped","suppressed","filtered","queue_len","last_http"(код или null),"last_ok","last_error","last_age_s"}`.
  `last_http` отрицательный — код транспортной ошибки HTTPClient (`last_error` — текст), тело ответа в API/лог не попадает.
- `POST /api/webhook` (пароль + `X-GS`): `url=.. method=.. body=.. ctype=.. err=.. tmo=.. min=.. insecure=0|1 en=0|1`, любое подмножество, применяется атомарно.
  Ошибка — 400 с текстом; неизвестный плейсхолдер: `unknown placeholder ${имя} (allowed: …)`.
- `POST /api/webhook/test` (пароль + `X-GS`): ставит `TEST` в очередь (409, если вебхук выключен/без URL). Результат — в `GET /api/webhook` и в Serial (`NOTIFY #id TAG -> ok http=200`; URL в лог не печатается).

### Шаблоны

В URL и теле работают `${host_name}`, `${event_message}`, `${event_value}`, `${event_tag}`, `${event_flags}`, `${event_time}`. Значения подставляются URL-кодированными
(как `urllib.parse.quote(s, safe='')`: без процента остаются только `A-Za-z0-9-_.~`, UTF-8 — побайтно). Это относится и к телу POST, поэтому тело — `application/x-www-form-urlencoded`
(для JSON-тела значения придут закодированными). `${…}` с именем из `[A-Za-z0-9_]*` и неизвестным именем (включая пустое `${}`) — ошибка при сохранении; всё остальное
(`$x`, `${a-b}`, `%`) — обычный текст.

| плейсхолдер | значение на плате |
|---|---|
| `${host_name}` | настройка `host` (по умолчанию `grid-supervisor`) |
| `${event_message}` | текст события (до 95 символов) |
| `${event_value}` | число с 2 знаками (`3040.00`, `47.30`) или пусто, если у события нет значения |
| `${event_tag}` | тег события (`CELL_LOW`, `CONNECT`, `BOOT`, …; см. ниже) |
| `${event_flags}` | текст: для флагов супервизора — все активные флаги (`HARD_LOW\|HOLD`), для `BMS_FLAGS` — `f<слот> mask=0x..`, иначе пусто |
| `${event_time}` | UTC `YYYY-MM-DD HH:MM:SS`; если время не синхронизировано — `uptime+<сек>s`. Событие, возникшее до NTP, получает время при отправке |

Отличия от прокси (там другой набор данных): у прокси `${event_tag}` — серьёзность (`ALERT|WARN|INFO`), `${event_value}` — вольты с 3 знаками, `${event_time}` — `YYYY-MM-DDTHH:MM:SSZ`, `${event_flags}` — число.
На плате `${event_tag}` — конкретный тег события, серьёзность в шаблон не попадает (её задаёт `webhook min`). Имена и правила подстановки/валидации те же.

Успех — HTTP 2xx и (если задан `err`) тело ответа не содержит эту подстроку. Редиректы не выполняются (3xx — сбой).

**Telegram-бот** (GET; токен и chat_id — свои, `%20` — пробел, `:` после тега остаётся):
```
webhook url "https://api.telegram.org/bot<TOKEN>/sendMessage?chat_id=<ID>&text=${host_name}%20${event_tag}:%20${event_message}"
webhook err "\"ok\":false"
webhook on
webhook test
```
То же POST-ом (тело в формате формы; `disable_web_page_preview` — пример постоянного параметра):
```
webhook url "https://api.telegram.org/bot<TOKEN>/sendMessage"
webhook method post
webhook body "chat_id=<ID>&disable_web_page_preview=1&text=${host_name}%20${event_tag}:%20${event_message}%20(${event_time})"
webhook on
```
Произвольный сервис в стиле прокси: `webhook url http://srv/reg_event.php?tag=${event_tag}&host=${host_name}&value=${event_value}&event=${event_message}`, `webhook err #ERROR`.

**https и сертификаты.** По умолчанию `insecure=1`: `WiFiClientSecure::setInsecure()` — шифрование есть, подлинность сервера не проверяется. Это осознанный компромисс для
устройства в LAN (нет хранилища CA, время поначалу не синхронизировано; перехват трафика позволит подсмотреть токен бота). `webhook insecure off` — не вызывать `setInsecure()`
(поведение проверки определяет библиотека Arduino-ESP32 в сборке; нужно синхронное время; при отказе — `last_error` в `GET /api/webhook`).

### Политика отправки

- **Серьёзность.** `info`=0, `warn`=1, `alert`=2; события ниже `webhook min` отбрасываются (счётчик `filtered`). По умолчанию `warn`: **`BOOT` и все `…_OK` (выход из состояния) — `info`, их не будет, пока не выставить `webhook min info`.**
- **Подавление повторов.** Одинаковые пара `tag`+`message` — не чаще раза в 60 с (счётчик `suppressed`); другая комбинация уходит сразу. Окно считается от последнего ПРИНЯТОГО события.
- **Лимит скорости.** Не более 10 попыток отправки в минуту всего (скользящее окно 60 с); остальное ждёт в очереди и не теряется, пока не вытеснено переполнением кольца (16, вытесняется самое старое, счётчик `dropped`).
- **Повторы.** Сбой (нет сети/таймаут/не 2xx/`err` в ответе): повтор через 5 с, ещё раз через 30 с; третья неудача — событие отбрасывается (`failed`), очередь молчит 120 с, чтобы не долбить недоступный сервис. События идут строго по порядку.
- `TEST` обходит фильтр серьёзности и подавление, но не лимит скорости.

### События и теги

| источник | теги (серьёзность) |
|---|---|
| триггеры BMS (`lib/gs_trig`) | `CELL_LOW` warn, `CELL_LOW_OK` info, `CELL_HARD` alert, `CELL_HARD_OK` info, `CELL_DELTA` warn, `CELL_DELTA_OK` info, `BMS_FLAGS` warn, `BMS_STALE` warn, `BMS_BACK` info. Сообщение — текст триггера |
| флаги ядра (по фронту; сообщение начинается с `supervisor:`) | вход: `HARD_LOW` alert, `CELL_HARD` alert, `NO_DATA` alert, `GRID_LOST_LOW` alert, `SAFE_MODE` alert, `CELL_BLOCK` warn, `RELAY_MISMATCH` warn, `CELL_LOW` warn, `SOFT_LOW` warn. Выход — info: `HARD_LOW_OK`, `CELL_HARD_OK`, `NO_DATA_OK`, `GRID_LOST_OK`, `SAFE_MODE_OK`, `CELL_BLOCK_OK`, `RELAY_MISM_OK`, `CELL_LOW_OK`, `SOFT_LOW_OK` (теги ≤ 15 символов). В режиме приёма (`mode sniff`) ядро не шагает — событий флагов нет |
| команды ядра | `CONNECT` / `DISCONNECT`, сообщение `grid CONNECT: reason=HARD_FLOOR, 47.3 V` (+`, bus write FAILED`, если запись на шину не удалась). alert при причинах `HARD_FLOOR`, `NO_DATA`, `SAFE_MODE`, иначе warn (`SOFT_LOW`, `CHARGED`, `MANUAL`) |
| запуск | `BOOT` info: `boot rev=<ревизия> reset=<причина сброса>[,safe]` (`POWERON`, `SW`, `PANIC`, `TASK_WDT`, `BROWNOUT`, …; `,safe` — плата в safe-mode) |
| тест | `TEST` |

Теги `CELL_LOW`/`CELL_HARD`(`_OK`) встречаются дважды: от BMS-триггера (порог по кадрам BMS, текст `cell low: min … mV`) и от флага ядра (таймер dwell, текст `supervisor: weakest cell …`) — различайте по сообщению.
